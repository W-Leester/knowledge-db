# 라이선스 룰 (바이브코딩용 에이전트 규칙)

> **용도**: 이 파일을 새 프로젝트의 규칙 파일(`CLAUDE.md`·`.cursorrules` 등)에 붙여넣거나 링크해서, AI 에이전트가 라이선스 사고를 구조적으로 막게 한다.
> **원칙**: 라이선스 사고는 "몰라서"가 아니라 "확인 단계가 없어서" 난다. 이 룰이 그 단계다.
> 법률 자문이 아니다 — 상업적으로 중요한 판단은 전문가 확인이 필요하다.

---

## 0. 이 프로젝트의 기본 설정 (프로젝트마다 채운다)

```
내 프로젝트 라이선스: MIT
배포 형태: [ ] 소스 공개만  [ ] 실행 파일 배포  [ ] 웹 서비스(SaaS)  [ ] 비공개
```

- **웹 서비스로 제공할 계획이면 AGPL 의존성은 절대 금지** — 배포하지 않아도 소스 공개 의무가 발생한다.
- 위 설정이 바뀌면 이 파일을 먼저 갱신하고 나서 코드를 만진다.

---

## 1. 절대 규칙 (에이전트가 반드시 지킨다)

1. **의존성은 제안만 하고, 사용자 승인 후에 설치한다.** 임의로 `npm install`·`pip install`을 실행하지 않는다.
2. **패키지를 제안할 때는 라이선스를 함께 명시한다.** 모르면 "라이선스 미확인"이라고 밝히고 추측하지 않는다.
3. **🔴 목록의 라이선스는 제안 자체를 하지 않는다.** 대체품을 찾아 제시하고, 없으면 그 사실을 보고한다.
4. **코드를 외부에서 가져와 붙여넣지 않는다.** 필요하면 출처와 라이선스를 밝히고 승인을 받는다 (Stack Overflow·블로그·GitHub 스니펫 포함).
5. **LICENSE 파일과 README의 라이선스 표기를 임의로 바꾸지 않는다.**
6. **비밀키·토큰·개인정보를 코드나 커밋에 넣지 않는다.** (라이선스와 별개지만 같은 게이트에서 점검)

## 2. 라이선스 3색 신호등

의존성을 판단할 때 이 기준으로 분류한다.

### 🟢 통과 — 자유롭게 사용
`MIT` · `Apache-2.0` · `BSD-2-Clause` · `BSD-3-Clause` · `ISC` · `Unlicense` · `CC0` · `Zlib`

- 의무는 대체로 "저작권 표시 유지" 뿐 → §4의 고지 파일에 기록.

### 🟡 확인 필요 — 사용자에게 물어본다
`LGPL-2.1` · `LGPL-3.0` · `MPL-2.0` · `EPL-2.0` · `CDDL` · `CC-BY` 계열

- 확인 포인트: **그 라이브러리 자체를 수정했는가?**(수정하면 그 부분 공개 의무), 링크 방식(동적/정적), 파일 단위 공개 의무 여부.
- 수정 없이 그대로 링크해 쓰는 경우는 대개 안전하나, 판단은 사용자에게 넘긴다.

### 🔴 중단 — 제안 금지, 발견 시 즉시 보고
`GPL-2.0` · `GPL-3.0` · `AGPL-3.0` · `SSPL` · `BUSL`(Business Source License) · `Elastic License` · **`UNLICENSED` / 라이선스 표기 없음** · `Commons Clause` 부착 · 커스텀 독점 라이선스

- **GPL/AGPL**: 내 코드까지 동일 라이선스로 공개해야 한다(전염) → MIT 배포가 불가능해진다.
- **AGPL**: 배포하지 않고 웹 서비스로만 제공해도 소스 공개 의무.
- **라이선스 없음**: "자유"가 아니라 "저작권 전부 보유" — 법적으로 사용 권한이 없다. GitHub 공개 ≠ 사용 허락.
- **SSPL·BUSL·Elastic**: 오픈소스가 아니다. 상업적 사용·클라우드 제공에 제한이 있다.

> **주의**: 전염 의무는 **배포 시점**에 발동한다. 내 컴퓨터에서만 쓰는 스크립트라면 GPL도 문제되지 않는다. 그러나 바이브코딩 결과물은 대개 GitHub에 올라가고(=배포), AGPL은 서비스 제공만으로 발동한다. **"나중에 공개할지도 모른다"면 처음부터 🔴을 피한다.**

## 4. 서드파티 고지 (THIRD-PARTY-NOTICES.md)

MIT·BSD 등 🟢 라이선스도 **저작권 표시 유지**는 의무다. 다음 형식으로 프로젝트 루트에 유지한다.

```markdown
# 서드파티 라이선스 고지

이 프로젝트는 다음 오픈소스를 사용합니다.

## <패키지명> (<버전>)
- 라이선스: MIT
- 저작권: Copyright (c) <연도> <저작자>
- 출처: https://github.com/...
- 전문: (LICENSE 전문 또는 링크)
```

- 배포 산출물에 소스가 포함되지 않는 형태(실행 파일·앱)라면, 앱 안의 "라이선스" 화면이나 함께 배포하는 문서에 포함한다.
- 갱신은 게이트 ③에서 — 의존성이 바뀔 때마다 손으로 고치지 말고 검사 명령 출력에서 생성한다.

---

## 5. 검사 명령 (생태계별)

```bash
# JS / TS
npx license-checker --summary                 # 요약
npx license-checker --failOn "GPL-3.0;AGPL-3.0;SSPL-1.0"   # CI에서 차단

# Python
pip install pip-licenses && pip-licenses --format=markdown

# Rust
cargo install cargo-license && cargo license

# Go
go install github.com/google/go-licenses@latest && go-licenses report ./...
```

- **CI에 걸어둔다**: 위 `--failOn` 류를 GitHub Actions에 넣으면 🔴이 들어오는 즉시 빌드가 실패한다 — 기억력에 의존하지 않는 방법.
- 검사 도구도 완벽하지 않다(라이선스 표기 누락·오탈자). 결과가 "UNKNOWN"인 항목은 🟡로 취급해 직접 확인한다.

## 6. AI 생성 코드에 대한 입장

- **AI가 생성한 코드 자체**: 저작권 보호를 받기 어려운 산출물로 보는 견해가 우세하다 → 내가 MIT로 배포하는 데 실무적 장애는 대개 없다.
- **다만 AI가 기존 코드를 상당량 재현한 경우**: 원본의 라이선스 문제가 남는다. 드물지만 유명 알고리즘·유명 저장소의 특징적 코드에서 발생할 수 있다.
- **에이전트 규칙**: 특정 프로젝트의 코드를 그대로 재현하지 않는다. 참고했다면 출처를 밝힌다.
- 이 항목은 법·판례가 변하는 영역이다 — 상업적 배포 전에는 최신 상황을 확인한다.

## 7. 내 프로젝트 라이선스 고르기 (참고)

| 상황 | 권장 |
|---|---|
| 개인 프로젝트·유틸·학습용 | **MIT** — 짧고 범용, 사실상 표준 |
| 기업이 갖다 쓸 것을 기대 / 특허가 얽힐 기술 | **Apache-2.0** — 특허 조항이 채택 장벽을 낮춘다 |
| 파생물도 반드시 공개시키고 싶다 | GPL-3.0 (단, 기업 채택은 급감) |
| 서비스형 무단 사용까지 막고 싶다 | AGPL-3.0 (같은 대가) |
| 공개하지 않을 코드 | LICENSE 대신 `UNLICENSED` 명시 + private 저장소 |

- 라이선스는 나중에 바꿀 수 있지만, **외부 기여자가 생기면 그들의 동의가 필요**해진다 → 초기에 정하는 것이 싸다.
- 문서·이미지 등 코드가 아닌 자산은 별도 라이선스(CC BY 등)를 쓰는 경우가 많다.

## 8. 에이전트를 위한 요약 (한 문단)

> 이 프로젝트는 MIT로 배포된다. 새 의존성은 **제안만 하고 설치하지 않으며**, 제안 시 반드시 라이선스를 명시한다. `GPL`·`AGPL`·`SSPL`·`BUSL`·`Elastic`·라이선스 표기 없는 패키지는 **제안하지 않는다**(대체품을 찾아 제시). `LGPL`·`MPL`은 사용자 판단을 받는다. 외부 코드를 붙여넣지 않고, 참고했으면 출처를 밝힌다. 의존성이 바뀌면 `THIRD-PARTY-NOTICES.md` 갱신을 함께 제안한다. 배포 전에는 라이선스 검사 명령 결과를 보고한다.
