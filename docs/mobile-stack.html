Kotlin은 언어, Flutter는 프레임워크

Kotlin · Flutter · Swift · React Native · KMP가 나란히 불리지만 서로 다른 층의 물건이다. 언어와 프레임워크와 툴체인을 먼저 갈라놓고, 네이티브와 크로스플랫폼의 지형을 그린 뒤, "무엇을 공유하고 무엇을 따로 만드나"라는 하나의 축으로 선택지를 정렬한다. 그리고 어느 길로 가도 바뀌지 않는 것 — 맥·서명·심사 — 까지.

프레임워크가 언어를 데려온다 — 이것이 모바일 이름이 헷갈리는 진짜 이유다. Flutter를 고르면 Dart가 따라오고, React Native를 고르면 JS·TS가 따라온다. 그래서 "프레임워크 선택 = 언어 선택"이 되어버리고, 두 층이 한 덩어리로 불린다. 「개발 생태계 해부」의 6층 명함으로 보면 1층과 5층이 짝을 이뤄 움직이는 셈이다.

구조가 거울처럼 겹친다. 양쪽 다 새 언어가 옛 언어를 대체했고(Java→Kotlin, ObjC→Swift), 선언형 UI가 명령형 방식을 대체했다(XML→Compose, UIKit→SwiftUI). 선언형이란 "화면이 이렇게 생겨야 한다"를 적으면 프레임워크가 알아서 갱신하는 방식이고, 구식은 "이 버튼의 글자를 바꿔라"를 일일이 지시하는 방식이다. 「애플 앱 개발의 지도」 §6-C에서 다룬 SwiftUI와 UIKit의 차이가 안드로이드에서 그대로 반복된다.

🪞
대칭이 주는 이점 — 한쪽을 제대로 배우면 다른 쪽의 학습 비용이 크게 줄어든다. 개념(화면 단위·생명주기·권한·상태 관리)이 같고 이름만 다르기 때문이다. 「애플 앱 개발의 지도」 §0-B의 안드로이드↔iOS 1:1 대응표가 그 번역기 역할을 한다.

3-2. 화면을 그리는 세 가지 방식 — 이 차이가 나머지를 정한다

§3 표에서 "Flutter는 직접 그리고 React Native는 OS 부품을 조종한다"고 한 줄로 적었는데, 이 차이가 앱 용량 · 화면 일관성 · OS 업데이트 대응을 전부 결정한다. 픽셀까지 가는 길을 나란히 놓으면 이렇다:

양 플랫폼 화면 차이당연히 다르다픽셀 단위로 같다미묘하게 다르다

🎨
축은 "OS를 얼마나 신뢰하나" — 신뢰할수록(네이티브·RN) 가볍고 최신에 붙지만 플랫폼의 제약을 받고, 신뢰하지 않을수록(Flutter) 일관되고 자유롭지만 엔진을 짊어지고 OS의 변화와 멀어진다. 브랜드 디자인이 강한 앱은 Flutter 쪽이, 플랫폼 표준을 따라야 하는 앱은 네이티브·RN 쪽이 편하다.

3-3. 같은 화면, 네 가지 코드 — 문법만 다르고 뼈대는 같다

버튼을 누르면 숫자가 오르는 화면을 네 스택으로 각각 써보면, §2에서 말한 "대칭"이 눈으로 보인다. 넷 다 ① 상태를 선언하고 ② 화면의 모습을 묘사하고 ③ 이벤트에서 상태를 바꾼다는 같은 뼈대다 — 이것이 선언형 UI의 공통 구조이고, 하나를 익히면 나머지의 학습 비용이 줄어드는 이유다.

Kotlin + Jetpack Compose — 안드로이드 네이티브@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }   // ① 상태
    Column {                                       // ② 모습
        Text("눌린 횟수: $count")
        Button(onClick = { count++ }) {            // ③ 이벤트
            Text("누르기")
        }
    }
}
Swift + SwiftUI — iOS 네이티브struct Counter: View {
    @State private var count = 0                  // ① 상태
    var body: some View {                         // ② 모습
        VStack {
            Text("눌린 횟수: \(count)")
            Button("누르기") { count += 1 }        // ③ 이벤트
        }
    }
}
Dart + Flutter — 양 플랫폼class _CounterState extends State<Counter> {
    int count = 0;                                 // ① 상태
    Widget build(BuildContext context) => Column(  // ② 모습
        children: [
            Text('눌린 횟수: $count'),
            ElevatedButton(
                onPressed: () => setState(() => count++),  // ③ 이벤트
                child: Text('누르기'),
            ),
        ],
    );
}
TypeScript + React Native — 양 플랫폼function Counter() {
    const [count, setCount] = useState(0);          // ① 상태
    return (                                          // ② 모습
        <View>
            <Text>눌린 횟수: {count}</Text>
            <Button title="누르기"
                onPress={() => setCount(count + 1)} />   // ③ 이벤트
        </View>
    );
}
🧩
넷이 닮은 것은 우연이 아니다 — 모두 웹의 React가 퍼뜨린 선언형 + 상태 기반 사고를 받아들였다. "버튼 글자를 바꿔라"라고 지시하는 대신 "상태가 이러면 화면은 이렇다"를 적고, 상태가 바뀌면 프레임워크가 알아서 다시 그린다. 그래서 진짜 학습 비용은 언어가 아니라 이 사고방식에 있고, 한 번 익히면 스택을 옮겨도 대부분 전이된다. 「기술 스택 고르기」 §5의 제어의 역전이 화면에 적용된 모습이다.

4. 제3의 길 — KMP, 그리고 그 외 선택지

"전부 공유"와 "전부 따로" 사이

Kotlin Multiplatform(KMP)은 절충안이다. 비즈니스 로직·네트워크·데이터베이스·검증 규칙처럼 화면이 아닌 부분만 Kotlin으로 공유하고, UI는 각 플랫폼의 네이티브로 따로 만든다(Compose와 SwiftUI). "중복의 대부분은 로직에 있고, 품질 차이는 UI에서 난다"는 판단이다. 2026년 들어 채택이 빠르게 늘고 있으며, UI까지 공유하려는 Compose Multiplatform이라는 갈래도 함께 자란다(개략).

선택지언어언제 고르나
Kotlin MultiplatformKotlinUI 품질은 네이티브로 지키되 로직 중복은 없애고 싶을 때. 안드로이드 팀이 이미 Kotlin을 쓸 때 자연스럽다
.NET MAUIC#사내 시스템이 마이크로소프트 진영일 때. 기업 내부 앱에서 강하다
Unity · UnrealC# · C++게임. 3D·물리·에셋 파이프라인이 필요하면 사실상 여기뿐
Capacitor · Ionic웹 기술이미 만든 웹 앱을 스토어에 올려야 할 때의 최단 경로
PWA웹 기술스토어를 거치지 않아도 될 때. 설치 없이 홈 화면에 추가 — 이 지식 베이스가 그 방식
🌐
PWA는 다른 축에 있다 — 나머지가 "어떻게 만드나"의 선택지라면 PWA는 "스토어를 거칠 것인가"의 선택지다. 심사·수수료·서명·연회비가 전부 사라지고 업데이트가 즉시 반영되지만, 푸시 알림·백그라운드 실행·하드웨어 접근에 제약이 남는다. 이 지식 베이스가 PWA인 이유도 그 계산이었다 — 개인 문서함에 스토어 관문은 과하다.

5. 저울 — 공유율이 오르면 무엇이 내려가나

공짜 점심은 없다

5-1. 공유율과 그 대가 (동적)

↩️
되돌리기 비용이 비대칭이다 — 네이티브에서 크로스플랫폼으로 가는 것보다, 크로스플랫폼에서 네이티브로 되돌아오는 것이 훨씬 비싸다 — 사실상 재작성이다. 「데이터베이스 완전 정리」 §9의 "이사 난이도"와 같은 논리이고, 그래서 모바일 스택 선택은 초기에 가장 비싼 결정이다. 확신이 없으면 공유율이 낮은 쪽(네이티브·KMP)이 되돌리기 쉽다.

5-2. 네이티브 모듈이 필요해지는 순간 — 크로스플랫폼의 탈출구

§5의 "문제가 깊어지면 결국 네이티브 코드를 써야 한다"는 추상적으로 들리지만, 실제로는 목록이 꽤 분명하다. 아래 항목이 요구사항에 있으면 크로스플랫폼을 골라도 각 플랫폼 코드를 따로 쓰게 된다 — 고를 때 미리 세어볼 값어치가 있다:

요구사항왜 네이티브로 내려가나
홈 화면 위젯위젯은 OS가 직접 그리는 영역이라 각 플랫폼 방식대로 만들어야 한다
백그라운드 작업앱이 꺼진 뒤의 동작 규칙이 양 OS에서 완전히 다르다 — 배터리 정책도 각자다
블루투스·NFC·USB기기 통신은 OS API에 밀착해 있어 래퍼로 덮기 어렵다
카메라 세밀 제어촬영 버튼 수준은 플러그인으로 되지만, 노출·초점·RAW로 들어가면 네이티브
OS 새 기능발표 직후에는 프레임워크 지원이 없다 — 먼저 쓰려면 직접 연결
특정 SDK만 제공되는 서비스결제·인증·지도 중 일부는 네이티브 SDK만 내놓는다
무거운 실시간 처리영상 필터·오디오 처리처럼 매 프레임 계산이 필요한 일 (온디바이스 모델 포함)

탈출구가 있다는 것이 크로스플랫폼의 설계 — Flutter와 React Native 모두 "필요하면 네이티브 코드를 붙일 수 있는" 통로를 제공한다. 문제는 그 통로를 쓰는 순간 그 기능만은 두 플랫폼을 따로 만들게 되고, 각 OS를 아는 사람이 필요해진다는 것이다. 그래서 실전의 질문은 "크로스플랫폼으로 전부 되나"가 아니라 "내 요구사항에서 탈출구를 몇 번 쓰게 되나"다. 세 번 이상이면 네이티브나 KMP가 오히려 단순할 수 있다.

7. 무엇을 골라도 바뀌지 않는 것

스택 선택이 면제해주지 않는 것들

상수내용
맥과 XcodeiOS 산출물은 어느 언어로 짰든 애플 툴체인을 통과해야 한다. Flutter·RN도 예외 없음 (「애플 앱 개발의 지도」)
서명과 인증서두 스토어 모두 서명을 요구한다. 키를 잃으면 업데이트를 못 낸다
심사와 정책계정 삭제·개인정보 라벨·ATT·타겟 API 의무 (「앱 출시의 관문」)
강제 업데이트 장치앱은 웹과 달리 구버전이 남는다 — 원격으로 막을 장치를 처음부터 (「앱 출시의 관문」 §3)
백엔드 선택스택과 무관하게 필요하다. 모바일이면 Firebase의 오프라인 동기화가 유리한 경우가 많다 (「데이터베이스 완전 정리」 §9-C)
라이선스 고지어떤 프레임워크를 쓰든 의존성 고지 의무는 남는다 (「오픈소스 라이선스와 바이브코딩」)
📌
맺음 — 모바일 스택의 이름들은 층으로 갈라 보면 정리된다. 언어(Kotlin·Swift·Dart·TS), 프레임워크(Compose·SwiftUI·Flutter·RN), 툴체인(Android SDK·Xcode). 선택의 축은 하나 — 무엇을 공유하고 무엇을 따로 만드나. 공유가 늘면 빨라지고, 플랫폼의 최신과는 멀어진다. 그리고 어느 길을 골라도 맥·서명·심사는 그대로 남는다 — 스택 선택은 만드는 방법을 바꿀 뿐, 스토어와의 관계를 바꾸지 않는다.
